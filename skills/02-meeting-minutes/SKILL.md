# 会议纪要

## 何时激活

- 用户说"会议纪要"、"整理会议记录"
- 用户说"拜访纪要"、"客户拜访记录"
- 用户说"工作会议"、"会议记录"
- 用户提供会议相关的语音转文字、聊天记录或要点列表

## 会议类型（自动识别）

- **visit** - 拜访纪要：客户拜访、现场交流、商务会谈
- **work** - 工作会议纪要：评审、对齐、复盘、站会、技术讨论

AI 按 R01→R05 级联判定类型，用户显式指定覆盖一切。

## 输出路径

```
output/meeting_minutes/
├── visit/{年份}/{日期}-{客户}.md
└── work/{年份}/{日期}-{主题}.md
```

## 拜访纪要格式

模板：`templates/visit-notes.md`

包含五大章节：客户情况 → 核心议题（结论先行）→ 合作机会 → 行动项（RK/客户方分组）→ 后续安排。

### 示例

```
西门子拜访纪要

日期：2025-12-29
地点：西门子上海办公室
参会人：RK：张三、李四；客户方：王经理（工业自动化事业部）、赵工（嵌入式平台组）

一、客户情况

  主营业务：工业自动化、数字化工厂、智能基础设施
  公司规模：全球工业自动化龙头，年营收超 700 亿欧元
  合作现状：评估 RK 芯片用于工业边缘计算场景
  决策链：王经理（事业部采购决策）、赵工（技术选型评估）

二、核心议题

  2.1 技术诉求
  客户需要低功耗、高算力的边缘计算方案，RK3568 的 SATA 接口是关键吸引点。
    - 功耗要求：严禁风扇，控制在 10-20W
    - 存储需求：看好 RK3568 SATA 接口，用于工业数据长周期本地存储
    - 控制需求：支持 30+ 轴控制，系统带宽从传统显示转向 AI 占用

  2.2 竞争格局
  Intel Atom 断供窗口期是 ARM 切入工业市场的战略机会。
    - Intel Atom 将断供（2032 年），边缘侧经验不足
    - Linux 市场大，ARM 在工业、车载、机器人领域有 x86 替换机会

三、合作机会

  产品需求：RK3568（边缘计算）、70 TOPS 算力芯片（AI 推理）
  预估量级：待确认（工业场景，预计年用量万级）
  时间节点：2025 Q2 完成选型评估，Q4 启动量产导入
  竞品态势：Intel Atom 断供在即，RK Linux 生态和功耗优势明显

四、行动项

  RK：
    - @张三 输出"70 TOPS + 20W 功耗"产品路径图，02/15
    - @李四 准备 RK3568 工业边缘计算 Demo 方案，02/20

  客户方：
    - 赵工 提供详细的轴控制和 AI 算力需求规格书，02/28

五、后续安排

  下次沟通：03/15 线上技术对接
```

## 工作会议纪要格式

模板：`templates/work-meeting.md`

包含五大章节：会议结论 → 讨论要点（结论先行）→ 风险与阻塞 → 行动项（按模块/截止日期分组）→ 后续安排。

### 示例

```
新版本开发会议纪要

日期：2026-02-05
参会人：张三、李四、王五、赵六
会议目标：对齐 Windows 平台、以太网、OTA 三大模块开发计划

一、会议结论

  1. Windows 平台 1 月底完成驱动、工具链、RKNN3 — 依据：客户 Q1 交付节点倒推，负责人：张三
  2. 以太网优先实现固件烧录和本地存储启动 — 依据：量产产线依赖此功能，负责人：赵六
  3. OTA 升级 2 月启动开发 — 依据：依赖以太网基础通信完成，负责人：王五

二、讨论要点

  2.1 Windows 平台
  USB/PCIe 驱动同步推进，RKNN3 采用命令行启动 rkllm-server。
    - 驱动层：USB 和 PCIe 双通道并行开发，确保兼容性
    - 应用层：RKNN3 服务采用命令行模式，降低集成复杂度

  2.2 以太网功能
  优先实现固件烧录和本地存储启动，底层封装通信接口。
    - 固件烧录通道为量产产线刚需，优先级最高
    - 通信接口统一封装，为后续 OTA 复用奠定基础

三、风险与阻塞

  1. 以太网硬件设计确认滞后 — 影响：阻塞固件烧录开发；应对：先基于现有硬件搭建软件框架；负责人：赵六

四、行动项

  Windows（01/31）
    - @张三 USB/PCIe 驱动开发
    - @李四 烧录工具、调试工具开发
    - @王五 RKNN3 服务 + 应用层

  以太网（01/31）
    - @赵六 固件烧录、通信接口、硬件确认

  OTA（02/28）
    - @王五 OTA 升级功能开发

五、后续安排

  下次会议：02/12 14:00
  会前准备：@各模块负责人 提交进度报告
```

## AI 归纳规则

AI 必须按以下规则处理用户输入，生成结构化会议纪要。

### 规则优先级（Priority Order）

当规则冲突时，AI 按以下优先级执行，高优先级覆盖低优先级：

- **P0** 用户显式指令（最高优先级）
- **P1** 信息真实性（禁止编造）
- **P2** 纪要可读性与管理价值
- **P3** AI 归纳规则（R01-R31）
- **P4** 模板完整性（最低优先级）

允许在必要时简化模板，而不是编造内容填充。

### A. 类型识别规则 (R01-R05)

1. **R01 关键词优先** — 输入含"拜访/客户/现场/商务"→ visit，含"评审/对齐/复盘/站会/技术讨论"→ work
2. **R02 结构推断** — 出现"客户方/我方"参会人分组 → visit
3. **R03 内容推断** — 出现产品选型/商务报价/竞品对比/采购意向 → visit
4. **R04 用户覆盖** — 用户显式指定类型覆盖一切自动判定
5. **R05 无法判定时询问** — 仅此一处允许反问用户，其余场景禁止反问

### B. 输入理解规则 (R06-R10)

6. **R06 接受任意格式** — 语音转文字、聊天记录、要点列表、完整笔记均可处理
7. **R07 自动识别参会人** — 提取参会人并按角色分组（RK/客户方，或统一列表）
8. **R08 自动提取日期** — 从输入文本提取日期，无法提取则使用当天日期
9. **R09 自动识别议题边界** — 通过话题转换、关键词变化切分议题
10. **R10 过滤口语填充** — 过滤口语化填充词（嗯、那个、就是说）和重复表述

### C. 信息抽象规则 (R11-R18)

11. **R11 结论先行** — 每个议题先写一句话结论/决策，再写支撑细节
12. **R12 事实与观点分离** — 明确标注"已确认"vs"待确认"，区分事实与推测
13. **R13 数字量化** — 保留所有数字信息（功耗、价格、时间节点、规模、用量）
14. **R14 技术决策补充影响** — 技术决策条目补充业务价值或阻塞解除影响
15. **R15 竞品信息结构化** — visit 类自动提取竞品对比维度（产品/价格/生态/交期）
16. **R16 商机信号提取** — visit 类自动识别采购意向、量产计划、预算信号、项目规模
17. **R17 风险自动提取** — 从讨论中识别阻塞项、外部依赖、不确定性，写入风险章节
18. **R18 行动项三要素** — 每条行动项必须包含 @负责人 + 任务描述 + 截止日期

### D. 推断与容错规则 (R19-R23)

19. **R19 日期缺失** — 使用当天日期，不编造
20. **R20 参会人缺失** — 写"待补充"，不编造姓名
21. **R21 截止日期缺失** — 写"待定"，不猜测时间
22. **R22 负责人缺失** — 写"@待分配"，不随意指派
23. **R23 客户概况缺失** — visit 类保留章节框架，内容写"待补充"

### E. 风格规则 (R24-R27)

24. **R24 工程管理语言** — 使用工程管理语言，避免口语化和冗余修饰
25. **R25 消除弱表达** — 消除"推进/跟进/持续"等弱表达，替换为具体动作
26. **R26 信息密度** — 每条不超两行，禁止流水账，只记关键信息
27. **R27 中英文混排规范** — 英文技术术语保留原文，中英文间加空格

### F. 格式规则 (R28-R30)

28. **R28 章节编号连续** — 一、二、三...连续编号，不跳号，不留空章节
29. **R29 行动项分组** — work 类行动项按模块/截止日期分组
30. **R30 行动项分方** — visit 类行动项分"RK"和"客户方"两组

### G. 信息稀疏规则 (R31)

31. **R31 信息稀疏模式** — 当输入信息不足以支撑完整纪要时：仅输出已确认信息，保留结构但允许章节合并或简化，使用"待补充"而非推测补全，禁止生成推断性事实，禁止扩写未出现内容。触发条件：输入少于 5 条有效信息、无明确议题或决策、多为闲聊或模糊表达

## 工作流程（7 步）

AI 内部按以下 7 步隐式推理，不向用户展示中间过程：

```
Step 1: 识别类型 — 按 R01→R04 级联判定 visit/work，无法判定执行 R05 询问
Step 2: 提取元数据 — 日期、参会人、地点、主题（R07-R08）
Step 3: 提取事实 — 逐段扫描，提取结论/决策/数字/风险（R11-R17）
Step 4: 抽象归纳 — 按模板结构重组，结论先行，补充影响（R11, R14）
Step 5: 生成行动项 — 确保三要素，缺失字段用占位符（R18-R22）
Step 6: 质量自检 — 检查章节完整性、编号连续、无空章节（R28）
Step 7: 管理价值检查 — 确认包含 ≥1 条明确结论或决策、≥1 条可执行行动项、已识别风险或不确定性（若存在）、已删除流水账描述、已消除弱表达；若不满足，自动重新抽象与压缩内容
```

## 格式要点

1. **结论先行** — 核心决策放最前面（R11）
2. **指名道姓** — 待办必须 @具体负责人（R18）
3. **按模块分组** — 待办事项按模块/截止日期分组（R29）
4. **日期统一** — 截止日期用 MM/DD 格式
5. **简洁直接** — 不记流水账，只记关键信息（R26）
6. **纯文本输出** — 不使用 Markdown 格式（无 #、**、--- 等），仅用序号和缩进组织结构，适合邮件直接粘贴
7. **隐式结论** — 议题结论直接陈述，不加"结论："标签
