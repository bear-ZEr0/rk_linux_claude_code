# 周报生成

## 何时激活

- 用户执行 `/work-summary` 命令
- 用户请求生成周报
- 用户说"写周报"、"整理周报"
- 每周五下午

## 数据来源

### 自动收集

1. **Gerrit 提交** → 开发工作
   - 提交记录、代码审核状态
   - 自动提取芯片平台（从 subject/project/branch）

2. **Redmine 问题** → 客户支持
   - 处理的问题列表
   - 自动提取：芯片平台、客户名称、产品类型、经销商

3. **OA 考勤打卡** → 工时来源
   - 从泛微 E-cology OA 获取每日打卡记录
   - 替代 Redmine 工时作为周报工时数据源
   - 工时规则：工作日打卡完整按时间差算，打卡缺失按 8h；周末有打卡按实际算（加班），无打卡为 0h

4. **邮件信号** → 其他工作
   - 从收件箱和已发送自动提取工作信号（会议、协调、讨论等）
   - 自动过滤 Gerrit/Redmine/Jenkins 等通知邮件
   - 按类别分组：会议、跨部门协调、技术讨论、项目沟通

### 人工确认

自动收集已覆盖大部分数据，请确认并修正：
1. 各项目的工时分配比例
2. 自动生成的风险和下周计划是否准确
3. 有无遗漏的离线工作（未通过邮件/Gerrit/Redmine 记录的）

## 周报格式

### 一、项目详情

按平台/项目归类，合并同类弱化低价值，只保留对阶段推进和客户导入有影响的关键事项。仅有单条的非关键平台合并到「其他」分组，关键里程碑平台即使单条也独立列出。同系列芯片统一使用产品线名称（RK1820/RK1828 → RK182X，RK3566/RK3568 → RK356X）：

```
**【RK182X】**
- [发布] SDK V1.0.0 发布文档收敛完成，模组生产资料同步更新，具备客户导入条件
- #603784 [理工睿行/mec] rockit_yolo_detect Demo 参考 — 紧急

**【RK3572】**
- [Bringup] 完成任务分配及开发任务拆解，进入基础适配，为 Q2 客户送样建立开发基线

**【RK3588】**
- #609597 [华睿/工业智能相机] R 核执行内存问题确认，进行中

**【Gongga2】**
- [收敛] Boot 配置及供电电源方案评估完成，确认量产供电架构

**【其他】**
- #601651 [远大创新/工业主板] RK3506 QT 编译兼容问题确认
- [维护] RK3128 Flash 驱动异常导致 rootfs 损坏问题协调排查
- 参与产品线年度复盘，对齐技术支撑方向
```

> **阶段小结**: RK182X 完成发布转入客户导入期；RK3572 进入 Bringup 建立 Q2 送样基线

### 二、风险前瞻

每条风险三段式：「原因 → 影响 → 当前控制动作」。原因为客观条件或依赖，影响为项目阶段或客户节点，控制动作为已采取的措施。禁止列计划或假设。2-3 条：

```
- [RK3572] 硬件未到位 → Bringup 启动受阻，影响 Q2 送样节点 → 软件侧先行完成 DTS 框架搭建
```

### 三、其他部门支持

用依赖关系描述跨部门协作，1-2 条。禁止使用"需要/请求/希望"等表述：

```
- RK186X 验证计划排期依赖 IC 设计部回片时间表作为前置输入
```

### 四、下周工作计划

每条明确交付物或阶段完成标志，2-3 条。禁止泛化描述：

```
- RK3572 完成 DTS 框架搭建及 UART/I2C 基础外设点亮验证
- RK182X 完成 SDK V1.0.1 补丁版本发布
```

## AI 归纳规则

脚本输出的是原始数据（含 `<!-- RAW_DATA -->` 标记），AI 必须按以下规则归纳后才能作为最终周报。

### 结构规则

1. **按平台归类** — "项目详情"按平台/项目归类，同一平台的开发、客户支持、评审等工作写在一起；仅有单条的非关键平台合并到「其他」分组，关键里程碑平台（Bringup/收敛/发布等）即使单条也独立列出
2. **平台名标准化** — 同系列芯片统一使用产品线名称：RK1820/RK1828 → RK182X，RK3566/RK3568 → RK356X。脚本已自动归一化，AI 归纳时如遇遗漏需手动合并
3. **控制条目数** — 同类工作自动合并，每章节 3-5 条，单条不超两行
4. **拆分尾部章节** — 风险前瞻、其他部门支持、下周工作计划各为独立章节
5. **分别推导三尾章节** — 分别推导「风险前瞻」（2-3 条）、「其他部门支持」（1-2 条）、「下周工作计划」（2-3 条）

### 表达规则

6. **阶段结果表达** — 禁止流水账（已处理/跟进/协调），改为阶段结果：进入××阶段/完成××收敛/建立××基线/解除××阻塞
7. **标注推进阶段** — 技术事项标注推进阶段（导入/Bringup/设计冻结/收敛/量产准备/验证/发布）
8. **工程管理语言** — 使用工程管理语言，避免口语化和冗余修饰
9. **删除低价值描述** — 删除低价值重复描述

### 保留规则

10. **邮件归入项目详情** — 技术邮件和非技术邮件统一归入「项目详情」对应平台分组，无法归类的放入「其他」分组
11. **不显示邮件元数据** — 不显示邮件封数、讨论轮次、日期
12. **英文转中文** — 英文 commit message 翻译为中文
13. **保留 Redmine ID** — 客户支持条目保留 `#ID` 前缀，便于追溯

### 视角强化规则

14. **阶段表达强化** — 阶段标注升级为「阶段 + 动作 + 当前状态」三段式，如 `[启动→开发] RK3572 Bringup 完成任务分配，进入基础适配`
15. **技术决策补充价值** — 技术决策条目补充业务价值或阻塞解除，如 `确认核心供电与接口方案，解除硬件设计阻塞`
16. **平台归类总结** — 按平台/项目归类，同一平台下合并开发、客户支持、评审等条目
17. **技术语言提升** — 行政化表述替换为技术管理语言，如 `参加会议` → `参与产品线年度复盘，对齐技术支撑方向`
18. **阶段性进展总结** — 项目详情末尾追加阶段小结（blockquote），如 `> **阶段小结**: RK182X 完成发布转入客户导入期...`
19. **统一生命周期术语** — 项目事项统一使用生命周期术语（导入 / Bringup / 设计冻结 / 收敛 / 量产准备），替代模糊的「启动/评审」
20. **项目详情补充业务影响** — 每条项目详情补充一句业务或项目影响，如 `为 Q2 客户送样建立开发基线`
21. **风险三段式** — 每条风险：「原因 → 影响 → 控制动作」，原因为客观条件，影响为项目/客户节点，控制动作为已采取措施，禁止列计划或假设
22. **下周计划可验证** — 下周计划包含可验证的阶段目标，而非泛化描述，如 `完成 DTS 框架搭建及 UART/I2C 基础外设点亮验证` 而非 `持续推进 Bringup`
23. **消除弱表达** — 消除"推进/跟进/持续"等弱表达，替换为具体动作，如 `输出根因分析报告，明确修复方案`
24. **依赖关系表达** — 其他部门支持用依赖关系描述（×× 依赖 ×× 作为前置条件），禁止"需要/请求/希望"等表述
25. **交付物明确** — 下周计划每条明确交付物或阶段完成标志（输出××报告/完成××验证/发布××版本），禁止泛化描述

## 工时校验规则（后台校验）

工时来源为 OA 打卡数据（Redmine 工时不再使用）。

### 工时计算规则

| 场景 | 规则 |
|------|------|
| 工作日，打卡完整，12:00 前上班且 19:00 前下班 | 下班 - 上班 - 1.5h（午餐） |
| 工作日，打卡完整，12:00 前上班且 19:00 后下班 | 下班 - 上班 - 2.5h（午餐+晚餐） |
| 工作日，打卡完整，12:00 后上班且 19:00 前下班 | 下班 - 上班（不扣餐） |
| 工作日，打卡完整，12:00 后上班且 19:00 后下班 | 下班 - 上班 - 1h（晚餐） |
| 工作日，打卡缺失 | 默认 8h |
| 周末/节假日，有打卡 | 按上述规则计算（加班） |
| 周末/节假日，无打卡 | 0h |

### 约束条件

| 项目 | 时长 |
|------|------|
| 正常工作日 | 5 天 |
| 每日正常工时 | 8 小时 |
| 工作日每日最大加班 | 3 小时 |
| 周六加班（可选） | 最多 8 小时 |

### 校验逻辑

总工时须在 40H ~ 63H 之间，低于 40H 警告，超过 63H 报错。

## 工作流程

### 步骤 1: 运行脚本收集原始数据

运行数据收集脚本，获取 Gerrit、Redmine、邮件和 OA 考勤数据，生成含 `<!-- RAW_DATA -->` 标记的 .md 文件。

### 步骤 2: AI 读取原始数据，按管理视角重写周报

1. 读取脚本生成的 .md 文件（含 `<!-- RAW_DATA -->` 标记）
2. 按平台/项目归类重组「项目详情」，同一平台的开发、客户支持、评审等工作写在一起
3. 阶段标注使用生命周期术语（导入/Bringup/设计冻结/收敛/量产准备）
4. 技术决策条目补充业务价值或阻塞解除
5. 每条项目详情用阶段结果表达，禁止流水账
6. 合并同类、控制条目数（3-5 条/平台），行政化表述替换为技术管理语言，消除推进/跟进等弱表达
7. 邮件信号归入「项目详情」对应平台分组，无法归类的放入「其他」分组
8. 项目详情末尾追加阶段小结（blockquote）
9. 分别推导「风险前瞻」（2-3 条，三段式：原因 → 影响 → 控制动作）、「其他部门支持」（1-2 条，依赖关系表达）、「下周工作计划」（2-3 条，明确交付物）
10. 删除 `<!-- RAW_DATA -->` 标记，覆盖写回文件

### 步骤 3: 展示归纳后的周报，提示用户补充

```
周报已归纳完成，请确认并修正：
1. 各项目的工时分配比例
2. 自动生成的风险和下周计划是否准确
3. 有无遗漏的离线工作
```

### 步骤 4: 工时校验 + 保存最终版本

后台校验总工时是否在合理范围内，保存最终周报。

## 配置说明

在项目根目录 `settings.json` 中配置数据源：

| 配置项 | 说明 |
|--------|------|
| `gerrit.url` | Gerrit 服务地址 |
| `gerrit.username` / `password` | Gerrit 认证信息 |
| `redmine.url` | Redmine 服务地址 |
| `redmine.username` / `password` | Redmine 认证信息（或使用 `api_key`） |
| `oa.url` | 泛微 OA 地址（如 `https://oa.rock-chips.com:8888`） |
| `oa.username` / `password` | OA 登录账号密码 |
| `email.username` / `password` | 邮箱认证信息（SMTP/IMAP 共用） |
| `weekly_report.author` | 周报作者姓名 |

### 数据收集脚本

```bash
python skills/01-work-summary/scripts/collect-weekly-data.py          # 本周数据（默认含 OA 工时）
python skills/01-work-summary/scripts/collect-weekly-data.py --json   # JSON 输出
python skills/01-work-summary/scripts/collect-weekly-data.py --no-oa     # 跳过 OA 考勤
python skills/01-work-summary/scripts/collect-weekly-data.py --oa-only    # 仅 OA 考勤
python skills/01-work-summary/scripts/collect-weekly-data.py --oa-only --oa-captcha ABCD  # 指定验证码
python skills/01-work-summary/scripts/collect-weekly-data.py --email-only  # 仅邮件信号
python skills/01-work-summary/scripts/collect-weekly-data.py --send-email  # 收集并发送邮件
python skills/01-work-summary/scripts/collect-weekly-data.py --help   # 所有选项
```

### 模块化架构

`collect-weekly-data.py` 通过动态 import 委托以下独立模块完成数据收集：

| 模块 | 路径 | 职责 |
|------|------|------|
| rk-gerrit | `99-common-tools/rk-gerrit/scripts/gerrit_client.py` | Gerrit 提交查询与统计 |
| rk-oa | `99-common-tools/rk-oa/scripts/oa_client.py` | OA 登录、考勤打卡、工时计算 |
| rk-redmine | `07-customer-support/rk-redmine/scripts/sync_my_issues.py` | Redmine 工时与问题查询 |
| rk-email | `99-common-tools/rk-email/scripts/email_config.py` | 邮箱 IMAP 配置 |

本脚本仅保留周报特有逻辑：芯片平台归一化、邮件信号收集、周报 Markdown 生成。
